Architecture & Design Plan

Tolerance Tool for Excel Test Datasheets

An Excel add-in that standardizes how engineers compute measurement tolerances on test-case datasheets — converting expected values through instrument scaling curves, applying a configured tolerance band, and writing the result back to the sheet.

Framework Excel-DNA Runtime .NET Framework 4.8 Target Excel 2016+ / M365, 64-bit Status Design — pre-implementation Date 2026-08-28

01 Overview & goals

Engineers lay out test cases in Excel. Every test case names a signal and records an Expected value, a Tolerance, an Actual reading, and a Pass/Fail result. Today the tolerance in each row is calculated by hand or by ad-hoc formulas that differ between engineers and projects. This tool makes that one operation consistent and auditable.

What the tool does

  • Maps a datasheet's own column names onto the five required parameters, so layouts can vary.
  • Resolves each row's System ID to a configured signal — by direct name match, or through one or more alias tables.
  • Imports per-signal configuration (scaling curve, signal type, module type, EU ranges) from spreadsheets or an Access database, joining several sources on a Universal ID.
  • Stores tolerance definitions in an editable XML library, keyed by signal type + module type.
  • Calculates the tolerance for each expected value — round-tripping through the signal's scaling curve when the tolerance is specified in raw units, or working directly in EU when it is already in engineering units.
  • Writes or checks the Tolerance column across the datasheet, leaving cell comments where a value already present disagrees.

Design principles

  • The math is a library, not an add-in feature. The calculation engine has no dependency on Excel and is fully unit-tested on its own.
  • Formulas live in configuration. Scaling curves and tolerance bands are expressions in config files, evaluated at runtime — not compiled code. Engineers can add a scale type without a rebuild.
  • Config travels with the workbook where it is workbook-specific (datasheet mapping, import source definitions); shared libraries (scale types, tolerances) are external files with a per-workbook override path.
  • Every applied value is reproducible from the stored configuration.

Alias tables

The datasheet's System ID usually contains the sensor name rather than equalling it, and different projects abbreviate differently — so resolution runs a ladder, and alias tables fill the gaps. Multiple tables are allowed; they are consulted in priority order (in-workbook tables before shared ones by default), first hit wins.

<AliasTables>
  <AliasTable name="Project X" priority="10">
    <Alias systemId="FT-201-A"        sensorName="FT-201" match="exact" />
    <Alias systemId="^(FT-\d+).*$"    sensorName="$1"      match="regex" />
    <Alias systemId="Loop 4 Pressure" universalId="UT-1002" match="exact" />
  </AliasTable>
</AliasTables>
Resolution ladder 1. exact match of System ID to a SensorName (case-insensitive, trimmed)  →  2. alias tables, by priority  →  3. auto-match: exactly one SensorName occurs as a whole-token substring of the System ID. Two or more candidates at step 3 is ambiguous and flagged, never guessed. ToleranceResult records which step matched.
Per-worksheet review Before any Apply/Check, the Datasheet Mapping pane shows a resolution review grid for the active sheet — every row's System ID, how it resolved (exact / alias / auto-match / unresolved / ambiguous), and the signal it landed on. The user confirms or corrects each; corrections are stored as a per-sheet override map in the workbook, which sits above the whole ladder.

Scale-type library

Each entry gives the two directions of the curve, as expressions over a single normalized variable x in [0,1]. Forward maps the EU fraction to the raw fraction; Inverse is its reciprocal function.

<ScaleTypes>
  <ScaleType name="Linear">
    <Forward>x</Forward>
    <Inverse>x</Inverse>
  </ScaleType>

  <!-- e.g. DP-flow: measured flow (EU) vs. differential pressure (raw) -->
  <ScaleType name="SquareRoot">
    <Forward>Pow(x, 2)</Forward>
    <Inverse>Sqrt(x)</Inverse>
  </ScaleType>

  <ScaleType name="Logarithmic">
    <Param name="decades" value="2" />
    <Forward>(Pow(10, x * decades) - 1) / (Pow(10, decades) - 1)</Forward>
    <Inverse>Log10(x * (Pow(10, decades) - 1) + 1) / decades</Inverse>
  </ScaleType>
</ScaleTypes>
Contract Every curve must satisfy Forward(0)=0, Forward(1)=1, and be monotonic on [0,1]. The config loader validates this numerically and refuses a curve that fails.

Tolerance library

Keyed by signalType + moduleType. A band is the sum of one or more typed terms. Each term declares its own space, so one library holds both raw-unit accuracy specs and ready-made EU tolerances.

TermAttributesMeaning
Percentvalue (fraction), basis = rawSpan (default) | euSpan | reading ±0.3% → value="0.003". Default is % of raw span — for 4-20 mA that is 0.3% × 16 = 0.048 mA, applied in raw space. euSpan uses the row's EU span (English or SI) and stays on the EU fast path.
AbsoluteEuvalue, unit, unitSystem = English | SI ±0.45 degF, ±0.5 rpm. Already in EU — no raw round-trip. Scaled by the EU-span ratio if the row's unit system differs.
AbsoluteRawvalue, unit A fixed raw offset (counts, mA). Forces the raw round-trip.
Expressionspace, NCalc body Escape hatch. Variables: rawExpected, rawLow, rawHigh, rawSpan, expected, euLow, euHigh, euSpan.
 
<Tolerances>
  <!-- current loop: 0.3% of raw span (default basis) -->
  <Tolerance signalType="4-20mA" moduleType="AI-871">
    <Percent value="0.003" />
  </Tolerance>

  <!-- RTD temperature: fixed 0.45 degF, already EU -->
  <Tolerance signalType="RTD-PT100" moduleType="AI-664">
    <AbsoluteEu value="0.45" unit="degF" unitSystem="English" />
  </Tolerance>

  <!-- speed pickup: fixed 0.5 rpm, already EU -->
  <Tolerance signalType="Tach-Pulse" moduleType="CI-220">
    <AbsoluteEu value="0.5" unit="rpm" unitSystem="English" />
  </Tolerance>

  <!-- composite: 0.1% of raw span + a fixed raw offset -->
  <Tolerance signalType="0-10V" moduleType="AI-664">
    <Percent value="0.001" basis="rawSpan" />
    <AbsoluteRaw value="0.002" unit="V" />
  </Tolerance>
</Tolerances>
Fast path When every term of a definition is EU-space (AbsoluteEu, or Percent basis="euSpan"), the engine skips the scale round-trip entirely: tolerance = Σterms, applied symmetrically about expected. The round-trip runs only when a raw-space term is present (Percent basis="rawSpan" — the default — or AbsoluteRaw).

06 Datasheet mapping

The five required parameters are fixed; the column headers that carry them are not. The mapping pane lets the user bind each one to a header in their sheet, exactly as sketched in the brief:

Required parameterWorksheet equivalent (example)Role
System IDSignal NameIdentifies the signal — matched to SensorName.
ExpectedExpect'dInput to the calculation (engineering units).
ToleranceTolOutput — written on Apply, compared on Check.
ActualActRead only; used for optional Pass/Fail.
Pass/FailPass/FailOptional output.

Mapping also captures

  • Orientation — row-oriented at launch (one test case per row, headers in a header row). Column-oriented sheets are a later phase; the field is stored now so the format does not change.
  • Header row — which row holds the headers; picked by click or by cell reference.
  • Data extent — first and last test-case row, or "to end of contiguous data".

The tool always operates on the active worksheet — the datasheet currently in focus. Mapping, resolution overrides, and precision policy are all stored per sheet, so a workbook can hold several datasheets and each keeps its own setup. Column resolution is by case-insensitive trimmed header match, with the mapped string stored so a moved column is re-found automatically. A missing or ambiguous header is reported before any calculation runs.

Unit system

The mapping carries a default unit system for the sheet — English or SI — because it is usually uniform across a datasheet. A per-row units column may also exist on some sheets but is not relied upon: if the user maps one and a row has a non-blank value, it overrides the sheet default for that row; otherwise the sheet default stands. Either way every signal is assumed to carry both its English (EuLow/EuHigh) and SI (EuLowSi/EuHighSi) ranges from import. An SI row is evaluated against the SI range and its result is in SI units; AbsoluteEu tolerance terms defined in the other system are converted by the ratio of the two configured EU spans.

System ID → signal

Each row's mapped System ID is resolved through the resolution ladder (exact name match → alias tables → auto-match). The tool attempts the auto-match, then the Datasheet Mapping pane presents a per-worksheet resolution review grid so the user confirms or corrects each row before Apply/Check; corrections persist as per-sheet overrides. Unresolved and ambiguous rows are listed and never guessed.

Tolerance precision

The mapping stores how the written value is rounded:

  • Match the Expected cell — count the significant digits shown in that row's Expected cell (from its displayed text, honouring its number format) and round the tolerance to the same count. This is the requested default-capable option.
  • Fixed — N significant figures, or N decimal places, applied to every row.
  • Rounding mode — half-up or half-to-even.

07 Signal configuration import

Two source kinds behind one interface. Both end at the same preview grid.

interface ISignalSource {
    string Name { get; }
    bool IsMaster { get; }
    IReadOnlyList<SignalFieldRecord> Read();   // keyed by UniversalId
}

Method A — CSV / XLSX files

  • The user selects one or more files. Each becomes a source.
  • Exactly one source is the master: the one that connects SensorName to UniversalId. The master's row count sets how many signals exist.
  • Every source declares where its Universal ID is (column letter for row-oriented data, row number for column-oriented) and must be non-blank there.
  • Every other mapped field declares its column (or, for a key/value sheet, the column holding the value on the Universal ID's row) and an optional required flag.
  • Sources are joined on UniversalId; a left join from the master.

08 Tolerance configuration

The Tolerance Editor is a grid over the tolerance XML: add, delete, modify. Each definition is one (signalType, moduleType) row with its band terms shown and editable inline. The editor:

  • adds terms by type (Percent / AbsoluteEu / AbsoluteRaw / Expression); validates Expression bodies (parse, known variables only) on edit;
  • shows a live preview: pick a sample signal and expected value, see each term resolved and the resulting ± band — and whether the fast EU path or the raw round-trip applies;
  • flags (signalType, moduleType) combinations present in the resolved signal set that have no tolerance defined — this is the gate for "Tolerance Configuration is ready";
  • loads from / saves to the shared library path, or a workbook-specific override.

The tolerance for a given datasheet row is selected by the signal's SignalType + ModuleType. No match → that row is reported and skipped (never silently zero).

09 The tolerance calculation

The expected value is in engineering units. How the band is applied depends on where the tolerance terms live:

  • Path A — all terms in EU. No conversion. tolerance = Σterms about expected (a Percent basis="euSpan" resolves against the row's EU span). Covers ±0.45 degF, ±0.5 rpm, ±0.3%-of-EU-span.
  • Path B — any term in raw units (including the default Percent basis="rawSpan"). The round-trip below. Because a non-linear curve makes a symmetric raw band asymmetric in EU, the written value is the larger of the two EU-side deviations.
EU space: expected, EuLow/High (or the SI pair for an SI row) raw space: RawLow, RawHigh curve: ScaleType.Forward / .Inverse

Path B steps

  1. Pick the EU range. Use EuLow/EuHigh for an English row, EuLowSi/EuHighSi for an SI row. The result stays in that system.

    euFrac = (expected − EuLow) / (EuHigh − EuLow)

  2. To the raw fraction through the scale curve.

    rawFrac = ScaleType.Forward(euFrac)

  3. To raw units. Direct: below. Reverse (Linear only): RawHigh − rawFrac × (RawHigh − RawLow).

    rawExpected = RawLow + rawFrac × (RawHigh − RawLow)

  4. Sum the raw-space terms from the tolerance definition.

    rawTol = Σ rawTermᵢ(rawExpected, rawSpan, …)

  5. Apply the band in raw units — no clamping.

    rawPlus = rawExpected + rawTol   rawMinus = rawExpected − rawTol

  6. Back to EU fractions through the inverse curve, extrapolating when a raw edge lies outside [RawLow, RawHigh] (the expression is simply evaluated past its endpoints).

    euFrac± = ScaleType.Inverse( (rawPlus/Minus − RawLow) / (RawHigh − RawLow) )

  7. Back to EU values, then add any EU-space terms outside the round-trip.

    EU± = EuLow + euFrac± × (EuHigh − EuLow)  ±  ΣeuTermᵢ

  8. The calculated tolerance is the larger EU-side deviation, rounded per the mapping's precision policy, then written to the Tolerance cell.

    tolerance = Max( |EU₃ − expected| , |EU₂ − expected| )
Extrapolation guard Linear curves extrapolate cleanly. SquareRoot / Logarithmic can go non-finite just outside their domain (root of a negative, log of ≤0). When ScaleType.Inverse returns a non-finite value the row is flagged (“band exceeds the sensor range and the curve is undefined there”) and its Tolerance cell is left untouched — rather than writing a bad number.
Implementation ScaleCurve compiles each expression once with NCalc and caches it; the engine calls Forward(double) / Inverse(double). Every intermediate — resolution path, raw values, both EU edges, the precision applied — is kept on ToleranceResult so the Check action and any audit view can show the full working.

10 Applying & checking

Both actions run against the active worksheet, and are enabled only once Signal Configuration is ready (resolved set complete for every signal the datasheet references) and Tolerance Configuration is ready (every needed signalType + moduleType has a definition).

Apply all calculated tolerances

  • Removes all tool-authored cell comments on the sheet first.
  • Computes the tolerance for every mapped test-case row.
  • Writes the value into the Tolerance column.
  • Rows with no signal match / no tolerance / an extrapolation warning are collected into a summary dialog; their Tolerance cells are left untouched and flagged.

Check current tolerances

  • Computes the same values but writes nothing to the Tolerance column.
  • Where the existing cell value differs from the computed value beyond a small relative epsilon, adds a cell comment: expected vs. found, the signal used, and the band applied.
  • Ends with a summary: count checked, count mismatched, count un-checkable.
Comments Classic notes (Range.Comment / AddCommentThreaded is not used). Tool comments carry a fixed marker prefix (e.g. [ToleranceTool]) and their cell addresses are also tracked in per-sheet workbook config, so "Clear Tool Comments" and the Apply pre-clean only ever remove the tool's own notes and never an engineer's.

Pass/Fail is out of scope for the first releases but the mapping already captures the column; a later action can set it from |Actual − Expected| ≤ Tolerance.
